This report covers Task 2: a reproducible Indic (Telugu) speech pipeline (Speech $\to$ ASR $\to$ LLM $\to$ Text Response), its own evaluation infrastructure, a real evaluation run on 129 examples across two acoustic conditions, and a research-extension bottleneck fix with an ablation. The code, tests, and exact commands to reproduce every number here are in this repository; see \texttt{README.md}. This document reports what was actually run and measured, not a projected or idealized result.

\section{System}

\texttt{config.yaml} $\to$ \texttt{asr.py} $\to$ \texttt{llm.py} $\to$ \texttt{pipeline.py}. Pipeline: \textit{Speech input $\to$ Whisper-family ASR (vasista22/whisper-telugu-small) $\to$ Qwen2.5-1.5B-Instruct $\to$ Telugu text response}. Both models stay resident on one GPU and are reused across the whole evaluation run; \texttt{evaluate.py} measures wall-clock ASR time, LLM time, and total pipeline time per sample, synchronized around CUDA kernels, excluding model loading.

\subsection{Model choice and a VRAM constraint}

The evaluation GPU (RTX 4060 Laptop, 8\,GB) had \textbf{\textasciitilde 6.5\,GB free VRAM}. The originally configured defaults --- \texttt{openai/whisper-large-v3} (\textasciitilde 3\,GB in fp16) and \texttt{Qwen2.5-7B-Instruct} (\textasciitilde 15\,GB in fp16) --- do not fit together on this hardware. \texttt{config.yaml} instead uses:

\begin{itemize}[leftmargin=1.4em]
\item \textbf{ASR:} \texttt{vasista22/whisper-telugu-small}, a Telugu-only fine-tune of Whisper-small (not the general-purpose \texttt{openai/whisper-small}). This substitution was not optional: the general \texttt{whisper-small} checkpoint, even with Telugu forced via the \texttt{language} argument, transcribed this corpus's Telugu audio into \textbf{Devanagari/Hindi-looking script} (e.g.\ the Telugu reference ``Tel\={a}ng\={a}\d{n}a r\={a}jadh\={a}ni \={e}di?'' (``What is Telangana's capital?'', written in Telugu script in the dataset) came back as Devanagari text that merely sounds similar) and hallucinated repeated tokens on several short clips --- a real capability gap in the smallest general multilingual Whisper checkpoint on a low-resource language, not a configuration bug. The first full clean-condition run under that checkpoint is still visible in this repository's history; its corpus WER was 2.56 (word-level garbage from the script mismatch), which is why it was discarded and re-run.
\item \textbf{LLM:} \texttt{Qwen2.5-1.5B-Instruct}, the smallest instruction-tuned member of the Qwen2.5 family.
\end{itemize}

A second, unrelated compatibility issue surfaced while switching checkpoints: \texttt{vasista22/whisper-telugu-small} ships a \texttt{generation\_config.json} that predates \texttt{transformers}' newer \texttt{language}/\texttt{task} validation path, and \textbf{raises \texttt{ValueError}} if either is passed to \texttt{generate()} at all (not only when set to an unsupported value) --- see \href{https://github.com/huggingface/transformers/issues/25084}{huggingface/transformers\#25084}. This reproduced identically on \texttt{transformers} 5.15.0 and 4.57.6, so it is a property of this specific checkpoint, not the \texttt{transformers} major version. Since the checkpoint is Telugu-only, forcing a language is unnecessary, so \texttt{asr.py} was changed to treat \texttt{asr.language: null} as ``do not pass \texttt{language}/\texttt{task} to \texttt{generate()} at all'' (instead of always forcing a value), and \texttt{config.yaml} sets \texttt{language: null} for this checkpoint. \texttt{requirements.txt} was relaxed from \texttt{transformers<5} to \texttt{transformers<6} (the environment this ran in had 5.15.0 installed); \texttt{verify\_task2.py} and its tests were updated for both changes.

\textbf{Reproducibility caveat on this specific checkpoint:} while pinning exact commit hashes for this report, \texttt{vasista22/whisper-telugu-small}'s config/tokenizer files and its \texttt{model.safetensors} resolved to \textbf{two different} \texttt{main} commits within the same evaluation session (\texttt{717212f9\ldots} for config/tokenizer, \texttt{9bde7686\ldots} for weights) --- most likely an upstream micro-commit to the repository during this session. Pinning either single hash broke loading (the other component's files are absent from that snapshot), so \texttt{config.yaml} leaves this one checkpoint's revision at \texttt{main} rather than a broken pin; \texttt{Qwen2.5-1.5B-Instruct}'s revision (\texttt{989aa7980e\ldots}) is pinned normally and was stable throughout.

\subsection{Dataset}

No recorded Telugu corpus is bundled with this repository or exists locally. \texttt{synthesize\_corpus.py} builds one: \textbf{129 template-generated Telugu factual Q\&A pairs} --- 29 Indian state/UT capitals (Telugu script, pattern \textit{``<place> r\={a}jadh\={a}ni\ \={e}di?''} $\to$ \textit{``<place> r\={a}jadh\={a}ni\ <capital>.''}, i.e.\ ``What is the capital of <place>?'' $\to$ ``The capital of <place> is <capital>.'' --- the exact pattern given in the assignment's own example) and 100 small addition problems spoken as Telugu number words (1--10, 20 possible sums) --- synthesized to speech with the open \texttt{facebook/mms-tts-tel} model. Two parallel corpora were built from this same question/answer set:

\begin{itemize}[leftmargin=1.4em]
\item \textbf{\texttt{corpus\_clean/}}: the synthesized audio as-is.
\item \textbf{\texttt{corpus\_noisy/}}: the same text resynthesized with additive white Gaussian noise at a fixed \textbf{0\,dB SNR} (signal and noise equal power).
\end{itemize}

This exceeds the assignment's ``at least 100 examples'' per condition and gives the required ``at least two acoustic conditions.'' Both corpora were built with \texttt{prepare\_data.py --limit 0}, so the same already-tested dataset-preparation tool runs the full count for both conditions (129/129 selected, 0 placeholder responses).

\textbf{What this dataset does and does not establish.} This is synthetic TTS speech, not real human recordings --- it says nothing about real speaker variation, accents, disfluency, or recording-channel effects. The clean and noisy corpora are \textbf{not byte-identical pairs of the same recording}: the TTS model's duration prediction was not seeded, so re-running synthesis (the clean corpus was generated once; the noisy corpus was regenerated once more at a harsher SNR, see \S3) produces a different underlying rendering of the same text, not the same waveform plus noise. The clean-vs-noisy gap below therefore reflects \textbf{both} the added noise \textbf{and} natural TTS-rendering variance, not noise in isolation. The noisy-baseline-vs-noisy-denoised comparison in \S3, by contrast, \textbf{is} exactly matched --- both runs evaluate the identical \texttt{corpus\_noisy/} audio files, varying only whether \texttt{denoise.py} runs before ASR --- and is the one the research-extension conclusion rests on.

\section{Baseline results: clean vs. noisy}

All numbers are from real model inference on all 129 samples, with 0 failed samples in every run (\texttt{outputs/evaluation/<condition>/report.json}).

\begin{center}
\begin{tabular}{lrrr}
\toprule
Metric & Clean & Noisy (0\,dB SNR) & Change \\
\midrule
Corpus WER & 0.2928 & 0.3377 & +0.045 (+15.3\% rel.) \\
Corpus CER & 0.0745 & 0.0964 & +0.022 (+29.4\% rel.) \\
Corpus RTF (total pipeline / audio) & 4.15 & 4.99 & +0.84 \\
Corpus ASR-only RTF & 0.50 & 0.59 & +0.09 \\
Mean ASR time (s) & 1.74 & 2.05 & +0.31 \\
Mean LLM time (s) & 12.71 & 15.42 & +2.70 \\
Mean response quality (ASR transcript) & 0.1657 & 0.1548 & $-$0.011 \\
Mean response quality (clean transcript) & 0.1687 & 0.1687 & (same reference) \\
Mean quality drop (clean $-$ ASR quality) & 0.0031 & 0.0139 & +0.011 \\
Exact-match response rate & 0 & 0 & --- \\
\bottomrule
\end{tabular}
\end{center}

WER/CER are ratios (not percentages) and the evaluator computes them from scratch via Levenshtein distance; see \texttt{evaluate.py}. The noisy condition shows a real, if moderate, degradation in transcription accuracy and a small further drop in downstream response quality. Mean LLM time also rose under the noisy condition --- with greedy decoding on a fixed-size prompt budget this is attributable to noisier transcripts (word insertions/substitutions) lengthening the prompt and sometimes triggering longer generations, not to any change in the LLM itself (\texttt{llm.py} is identical and \texttt{Qwen2.5-1.5B-Instruct} was not touched between conditions).

\textbf{The dominant quality bottleneck is the LLM, not the ASR.} Comparing \texttt{asr\_response\_quality} (answer generated from the noisy ASR transcript) against \texttt{clean\_response\_quality} (answer generated from the ground-truth transcript, same LLM, same question) isolates ASR's downstream effect: even with a \textbf{perfect} transcript, mean response quality is only \textbf{0.169} out of 1, and the exact-match rate is \textbf{0 out of 129} in every condition. Manual inspection of sample outputs (e.g.\ \texttt{corpus\_clean/question\_cap-001.wav}, ``What is Telangana's capital?'') shows \texttt{Qwen2.5-1.5B-Instruct} frequently failing to state the short correct answer at all, instead producing repetitive, loosely-related Telugu text that never names the capital. This is a genuine capability limit of the smallest Qwen2.5 checkpoint on Telugu factual recall and instruction-following, not an artifact of the ASR stage or the evaluation harness --- and it is a legitimate instance of the assignment's ``hallucination rate'' criterion: the model answers confidently and fluently in Telugu without being correct, rather than declining. Fixing this would require a larger LLM, which circles back to the VRAM constraint in \S1.1.

\section{Research extension: a measurable bottleneck and an attempted fix}

\textbf{Bottleneck.} The noisy condition's ASR WER (0.3377) is measurably worse than clean (0.2928) --- see \S2. An \textbf{initial} noisy corpus built at 8\,dB SNR showed almost no WER change (0.2913 vs.\ 0.2928 clean --- i.e.\ no real bottleneck to fix), so the noise level was increased to 0\,dB SNR (noise power equal to signal power) specifically to produce a bottleneck large enough to be worth addressing; \S2's noisy numbers are from that 0\,dB corpus.

\textbf{Fix.} \texttt{denoise.py} implements magnitude spectral subtraction: estimate a per-frequency noise floor from each STFT bin's low time-percentile magnitude, subtract it (with a floor to limit musical-noise artifacts), and resynthesize with the original phase (Boll, 1979 --- a standard technique, not a novel one). It runs before ASR when \texttt{asr.denoise: true} (\texttt{config\_denoised.yaml}), on exactly the same \texttt{corpus\_noisy/} audio files used for the noisy baseline.

\begin{center}
\begin{tabular}{lrrr}
\toprule
Metric & Noisy, baseline & Noisy, denoised & Change \\
\midrule
Corpus WER & 0.3377 & 0.3391 & +0.0014 \\
Corpus CER & 0.0964 & 0.0992 & +0.0028 \\
Mean ASR time (s) & 2.05 & 2.03 & $-$0.03 \\
Mean response quality (ASR transcript) & 0.1548 & 0.1547 & $-$0.0001 \\
\bottomrule
\end{tabular}
\end{center}

\textbf{Result: the implemented fix did not help, at its default parameters (\texttt{oversubtraction=1.5, floor=0.05}) --- WER and CER both moved slightly in the wrong direction}, within what is plausibly run-to-run noise at this sample size. Latency overhead was negligible (denoising is cheap relative to ASR/LLM inference).

Before accepting that as final, a quick 25-sample ASR-only sweep (same checkpoint, no LLM stage, to keep iteration fast) compared the default (``mild'') setting against a more aggressive one (\texttt{oversubtraction=3.0, floor=0.02}):

\begin{center}
\begin{tabular}{lr}
\toprule
Setting & Mean WER (25-sample subset) \\
\midrule
No denoising (baseline) & 0.5433 \\
Mild (\texttt{oversubtraction=1.5, floor=0.05} --- shipped default) & 0.5300 \\
Aggressive (\texttt{oversubtraction=3.0, floor=0.02}) & 0.5567 \\
\bottomrule
\end{tabular}
\end{center}

On this smaller slice, mild subtraction gave a small improvement ($-$2.4\% relative WER) while aggressive subtraction made things \textbf{worse} than no denoising at all --- consistent with spectral-subtraction theory: over-aggressive subtraction introduces ``musical noise'' (isolated spurious spectral peaks) that a neural ASR model can be more sensitive to than to the original stationary noise. Since the ``mild'' setting here is exactly \texttt{denoise.py}'s shipped default, the 25-sample result does not contradict the full 129-sample result above --- it shows the technique's effect is small, inconsistent across subsets of this dataset, and not clearly distinguishable from noise at this sample size, while more aggressive tuning is actively counterproductive. A direct waveform-level check (\texttt{spectral\_subtract\_denoise} on one sample) confirms the filter is doing something sensible --- it reduces RMS energy (0.228 $\to$ 0.177) and reduces mean-squared error against an independently-synthesized clean rendering of the same text (0.094 $\to$ 0.073) --- so this is a negative result for whether that signal-level cleanup \textit{survives through the ASR model} into fewer transcription errors, not evidence the implementation is broken. The honest conclusion is: spectral subtraction, as implemented and at the noise level evaluated, does not reliably reduce WER for this ASR checkpoint, and over-tuning it is actively harmful. \texttt{tests/test\_denoise.py} covers the filter directly (noise-power reduction on a synthetic bursty-tone signal, input validation, short-signal passthrough) independent of this result.

\section{Limitations}

\begin{itemize}[leftmargin=1.4em]
\item \textbf{Synthetic speech only.} Every number above is on TTS-synthesized audio, not real Telugu speakers; real speech would exercise accent, prosody, and channel variation this corpus cannot.
\item \textbf{Small models, by hardware necessity, not choice.} A larger ASR/LLM pair would very likely change both the WER baseline and the LLM's factual accuracy substantially; \S1.1 explains the VRAM constraint behind the substitution.
\item \textbf{Response quality is a lexical proxy} (multiset word-overlap F1), not a semantic correctness judge --- a correct paraphrase can score low, and a wrong-but-word-similar answer can score higher than it deserves. \texttt{evaluate.py} supports substituting a custom scorer.
\item \textbf{Clean/noisy are not matched recordings} (\S1.2) --- the noisy-vs-clean WER gap includes unseeded TTS rendering variance, not noise alone. The baseline-vs-denoised comparison in \S3 does not have this issue.
\item \textbf{\texttt{vasista22/whisper-telugu-small}'s revision is unpinned} (\S1.1) due to the two-commit inconsistency observed during this run.
\end{itemize}
