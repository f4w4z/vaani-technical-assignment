Tests

30 unit tests in 8 files, all offline: no model downloads, no GPU, no network. They protect the evaluation code, which is where a silent bug would quietly corrupt every reported number.

python -m unittest discover -s tests -v

Expected: Ran 30 tests and OK in about two seconds. Use -s tests: the folder is not a package, so python -m unittest tests.test_x will not import.

What passing means It means the metric arithmetic, dataset handling, config guards, plotting and the denoise, hallucination and bootstrap logic behave as specified on constructed inputs. It does not mean the models are accurate; model quality is measured by the evaluation, not by the tests.

Notable details

Metrics are checked against hand-computed values

test_evaluate.py and the self-check inside verify_task2.py use fixed cases with known answers (perfect match, substitution, deletion, insertion, empty reference, Unicode normalization), so a regression in the edit-distance code shows up as a mismatch rather than a plausible-looking number.

Models are replaced by stand-ins

Pipeline and evaluation tests inject simple fake ASR and LLM objects, and the verifier test patches from_pretrained to fail if a download is attempted, so they run anywhere. The wrappers' audio handling is tested on tiny generated WAV files.

Bad input must fail loudly

Several tests assert errors rather than success: malformed datasets, duplicate IDs, missing audio, wrong-shaped plot data, a wrong metric value in the verifier, an out-of-range denoise parameter, a mismatched bootstrap pair. The project's rule is that invalid data should never be silently dropped or plotted.

A test that was wrong first

The first denoise test used a constant sine tone, and failed (error went up, not down). The cause was the algorithm's assumption that each frequency bin has quiet frames, which a sustained tone does not. The test was corrected to use a bursty tone with gaps, which resembles speech, rather than weakening the assertion. See the extension page.
